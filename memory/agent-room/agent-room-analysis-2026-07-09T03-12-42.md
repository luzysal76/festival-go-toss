## Round 2 — Stage 2: 약점 탐지자 ✅

### 치명적/중요 약점 목록

**1. 우선순위 부재 — 가장 심각한 누락**
(a)~(g) 7개 항목이 모두 "동등하게 다뤄야 할 요구축"으로만 나열되어 있고, 상대적 우선순위·구현 난이도·임팩트에 대한 판단 기준이 전혀 없음. ttapp 환경은 "실행모드 진입 시 한 번에 전체 작업을 완료"해야 하는 세션 구조(CLAUDE.md)인데, 7개 대형 기능축(플래너/주차/맛집/숙소/정산/쿠폰/앨범)을 모두 동시에 고도화하는 것은 단일 세션 내 구현 범위를 초과할 가능성이 높음. 2단계 설계안에 "MoSCoW"든 "Phase 1/2"든 우선순위 체계가 없으면 4단계(구현) 단계에서 범위 폭주 또는 미완성 위험이 큼.

**2. localStorage의 실제 환경 리스크 미검증**
1단계는 "기기/브라우저 종속적 데이터 유실 가능성"만 언급했는데, 더 구체적인 리스크가 빠짐: 토스 인앱 미니앱은 WebView 기반이며, 앱 업데이트·캐시 정리·토스 앱 자체의 스토리지 정책에 따라 localStorage가 예고 없이 초기화될 수 있음. "개인화(과거 방문 이력)"라는 핵심 요구사항(b)이 이 리스크에 정면으로 걸려 있는데, 대응 전략(예: 초기화 시 우아한 폴백, 데이터 없음 상태의 UX)이 설계 체크포인트에 없음.

**3. 목업 데이터 자체의 "다양성 부족" 문제 미인지**
필터링/정렬 로직(d)을 고도화하려 해도 현재 데이터가 맛집 3~5개, 숙소 3개, 쿠폰 3개 수준으로 극소량임. 데이터셋 자체를 확장(속성 다양화: 가격대, 태그, 좌표, 인원수 등)하지 않으면 "정교한 필터링 로직"을 만들어도 체감 효과가 거의 없음. 1단계 설계 체크포인트에 "데이터 스키마 확장" 항목이 빠져 있어 2단계에서 로직만 정교화하고 데이터는 그대로 두는 실수가 발생할 수 있음.

**4. 정산 플로우(c) 범위가 여전히 미확정 상태로 다음 단계에 위임됨**
1단계도 이를 인지는 했으나("범위를 먼저 못박고 설계 시작해야 함") 실제로 확정하지 않고 그대로 넘김. 이는 책임 회피에 가까움 — 2단계에서 "실제 송금 미연동 유지 + 시뮬레이션/공유 링크 고도화"로 명확히 못 박지 않으면, 설계자가 임의로 범위를 넓혀 토스 결제 API 연동을 암시하는 UX(예: 실제 송금 상태 추적)를 설계할 위험이 있고, 이는 토스 심사 재제출 리스크(딥링크 3종 구조 변경)로 이어질 수 있음.

**5. 딥링크 구조와 신규 기능의 충돌 가능성 — 검토 깊이 부족**
"딥링크 구조를 깨지 않는 선에서" 라는 원칙만 있고, 실제로 (b) 개인화, (d) 필터링/정렬 등이 새로운 화면 상태나 쿼리 파라미터를 요구할 경우 기존 intoss:// 딥링크 3종(플랜/주차/정산)의 진입점과 신규 UI 상태가 어떻게 매핑되는지에 대한 구체적 검토가 없음. 3단계에서 딥링크별 진입 시나리오를 실제로 트레이싱해봐야 함.

**6. 수익화(e) 항목의 현실성 미검토**
백엔드/결제 SDK 없는 순수 정적 웹앱에서 "수익화"는 사실상 시뮬레이션(쿠폰 UI, 광고 배너 UI)에 그칠 수밖에 없는데, 1단계 분석에는 이 현실적 한계에 대한 명시가 전혀 없음. 다음 단계가 "실제 결제 연동"을 암묵적으로 전제한 아이디어(예: 실제 쿠폰 발급 API)를 설계하면 범위 밖(Out of scope) 위반이 발생함.

**7. i18n 규칙과의 잠재적 충돌 미검토**
CLAUDE.md는 "신규 UI 텍스트 작성 시 다국어 지원 여부를 반드시 사용자에게 확인" 하도록 규정하는데, 1단계 분석에는 이 체크가 전혀 등장하지 않음. 지역축제 특성상 외국인 관광객 대응(다국어) 여부가 실제 요구사항일 수 있어, 늦어도 4단계 착수 전에는 이 확인 절차가 계획에 포함되어야 함.

**8. app.js 모듈 분리(g)의 실행 가능성 리스크**
CLAUDE.md 500라인 규칙과 연동은 잘 짚었으나, 정적 웹앱(빌드 도구 없음, ES module import 미확정)에서 `js/planner.js` 등으로 파일을 쪼갤 경우 `<script type="module">` 또는 다중 `<script>` 태그 로딩 순서/전역 스코프 문제를 어떻게 해결할지에 대한 기술적 검토가 없음 — "분리한다"는 방향만 있고 "브라우저에서 실제로 어떻게 로드되는가"에 대한 실현가능성 확인이 빠짐.

### 1. 우선순위 체계 (약점 #1 해결) — Phase 구조

| Phase | 항목 | 이유 |
|---|---|---|
| **P1 (Must)** | localStorage 상태관리 기반 구축, 플래너 입력 반영, 정산 다중분담 고도화, app.js 모듈 분리 | 다른 모든 기능의 기반 구조 + 사용자가 명시적으로 지목한 g,c |
| **P2 (Should)** | 개인화(방문이력/취향), 맛집·숙소·쿠폰 필터링/정렬 고도화 + 데이터셋 확장 | b, d — P1 상태관리 위에 얹는 기능 |
| **P3 (Could)** | PWA 완성도(아이콘/매니페스트), 리텐션 배지, 접근성(ARIA) | f, e — 시각적/부가가치 항목, 시간 남으면 |

### 2. localStorage 데이터 스키마 (약점 #2, #3 해결)
```js
// storage.js 가 관리하는 단일 네임스페이스
const STORAGE_KEY = 'festivalGo_v1';
{
  user: { visitCount: 0, lastVisitAt: null, preferredTags: [] }, // 취향 태그 누적
  planner: { lastInput: '', savedTimelines: [] },
  parking: { favoriteLotId: null },
  settlement: {
    sessions: [ // 여러 정산 세션 지원
      { id, title, members: [{name, ratio}], items: [{name, amount, payerId, splitType:'equal'|'ratio'|'item'}], status: 'draft'|'requested'|'completed', createdAt }
    ]
  },
  coupons: { usedIds: [], savedIds: [] },
  album: { photos: [] } // dataURL 기반, P3 이후 검토
}
```
- **초기화 대응(약점 #2)**: `storage.js`에 `safeGet()/safeSet()` 래퍼 — try/catch로 QuotaExceeded, SecurityError, 파싱 실패를 모두 잡고 `{}` 폴백. 앱 진입 시 데이터가 없으면 "처음 오셨나요?" 온보딩 카드를 자연스럽게 노출해 빈 상태를 UX로 흡수(에러 취급 안 함).
- **데이터셋 확장(약점 #3)**: 맛집 8~10개, 숙소 6개, 쿠폰 6개로 확대하고 각 항목에 `tags[], priceRange, coordDummy{lat,lng}, capacity, hasKidsMenu` 등 속성 추가 — `data.js`에 정적 배열로 분리.

### 3. 정산 플로우 고도화 (약점 #4 범위 확정 반영)
- 분담 방식 3종: 1/N 균등 / 인원별 비율(%) / 항목별 지정(누가 무엇을 먹었는지)
- `settlement.js`: `calcSplit(session)` → 인당 금액 계산, `generateShareText(session)` → 공유용 텍스트+링크 문자열 생성, `updateStatus(id, status)`
- 공유 UX: 기존 Web Share API + 클립보드 폴백 재사용, 공유 시 정산 세션 status를 'requested'로 자동 전환

### 4. 필터링/정렬 로직 (약점 #3와 연결)
- `filters.js`: `filterByTags()`, `sortByDistance()`(더미 좌표 기반 유클리드 근사), `sortByPrice()`, `recommendByHistory(userPrefs)` — 방문 이력의 `preferredTags`와 매칭 스코어링(가중치 기반 단순 태그 교집합 카운트)

### 5. 딥링크 호환성 검토 (약점 #5 해결)
기존 3종(`intoss://festivalgo/plan`, `/parking`, `/settlement`) 진입 시 신규 상태(필터값, 정산 세션 id 등)는 **URL 파라미터로 확장하지 않고** 진입 후 앱 내부에서 localStorage의 마지막 상태를 복원하는 방식으로 처리 → 심사 문서 변경 불필요. 단, `settlement` 딥링크는 새 세션 생성 화면으로 랜딩하도록 고정.

### 6. i18n 체크포인트 (약점 #7 해결)
4단계 시작 시 "이번 신규 UI 텍스트(정산/필터/개인화 문구)는 한국어 단일 언어로 진행합니다 — 다국어 필요하시면 알려주세요" 1줄 확인 후 진행(응답 없으면 단일 언어 기본값 유지, 작업 막지 않음).

### 7. 모듈 분리 구조 (약점 #8 해결) — 브라우저 네이티브 script 태그 유지
빌드 도구 없이 동작해야 하므로 ES module이 아닌 **다중 `<script>` 순차 로딩 + 전역 네임스페이스 객체**(`window.FG = {...}`) 패턴 채택:
```
js/
 ├─ storage.js    (FG.storage)
 ├─ data.js       (FG.data) — 확장된 목업 데이터
 ├─ planner.js    (FG.planner)
 ├─ parking.js    (FG.parking)
 ├─ food.js       (FG.food)
 ├─ lodging.js    (FG.lodging)
 ├─ settlement.js (FG.settlement)
 ├─ coupons.js    (FG.coupons)
 ├─ filters.js    (FG.filters) — 공용 유틸
 └─ main.js       (기존 app.js 잔여 — 탭 네비게이션, 초기화, 이벤트 바인딩만)
```
`index.html`에 로딩 순서대로 `<script src="js/storage.js"></script>` … `main.js`를 마지막에 배치. 각 파일 500라인 이내 유지.

### 8. PWA/접근성 (P3)
- `manifest.json`에 `icons` 배열 추가 필요 — 192x192, 512x512 PNG 2개 파일명만 정의(`icon-192.png`, `icon-512.png`), 실제 이미지 생성은 구현 단계에서 단색 배경+텍스트 로고로 임시 제작
- 주요 인터랙션 요소에 `aria-label`, 포커스 가능한 탭 순서 점검

### 1. 종합 실행 가능성 평가

1~3단계를 통합한 최종안은 사용자가 요구한 (a)~(g) 7개 축을 모두 커버하면서, 2단계에서 지적된 8개 약점을 구조적으로 해소했습니다.

| 검증 항목 | 판단 |
|---|---|
| 우선순위/범위 폭주 방지 | ✅ 3-Phase MoSCoW로 단일 세션 구현 범위 내로 수렴 |
| localStorage 리스크 대응 | ✅ safeGet/safeSet 폴백 + 온보딩 UX로 초기화 리스크를 에러가 아닌 정상 흐름으로 흡수 |
| 목업 데이터 빈약 문제 | ✅ 데이터셋 확장 + 속성 다양화(tags/price/coord/capacity) 명시 |
| 정산 범위 확정 | ✅ "실제 송금 미연동" 명문화, 시뮬레이션 고도화로 범위 고정 — 토스 심사 리스크 차단 |

### 2. 최종 권고사항 (구현 단계 착수 전 반영 권장)

1. **앨범(사진 자동분류) 기능 설계 공백** — 7개 기능 중 유일하게 P3에 "검토" 수준으로만 남아있음. 실제 업로드는 `<input type="file">` + FileReader로 dataURL을 localStorage에 저장하되, 용량 문제(QuotaExceededError)가 다른 기능보다 크므로 photos 배열에 개수 상한(예: 최대 20장) 또는 리사이즈 로직을 구현 단계에서 반드시 함께 정의할 것.
2. **화면별 UI 플로우 다이어그램 부재** — 데이터 모델과 함수 스펙은 충분하나, 탭별 화면 전환/컴포넌트 배치는 텍스트로만 암시됨. 구현 단계에서 각 Phase 착수 시 화면 단위로 먼저 마크업 스켈레톤을 잡고 진행 권장.
3. **PWA 아이콘 실제 생성** — 파일명만 정의되어 있으므로 구현 시 canvas 기반 단색 로고로 즉석 생성 후 172x192/512x512 PNG로 export하는 스크립트 한 줄 필요.
4. **정산 다중 세션 UX 복잡도** — `settlement.sessions` 배열 구조는 유연하지만, 사용자에게는 "여러 정산 세션" 개념이 과할 수 있음 — 구현 시 기본값은 세션 1개(활성 정산)만 노출하고 히스토리는 별도 탭/토글로 숨기는 방식 권장.
5. **CLAUDE.md 500라인 규칙 검증** — `data.js`가 8~10개 맛집+6개 숙소+6개 쿠폰 데이터를 모두 담으면 라인 수 초과 가능성 있음 → `data-food.js`, `data-lodging.js`, `data-coupons.js`로 추가 분리 여지를 구현 단계에서 재확인.
